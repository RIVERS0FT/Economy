# Economy 统一资产订单簿设计

> 状态：商品和工厂交易、成交价格、市场需求订单与估值的当前权威设计
> 适用项目：`RIVERS0FT/Economy`
> 更新时间：2026-08-24
> 客户端状态版本：36
> 世界状态版本：32
> 市场需求模型版本：19

模型 18 延续实际人口稳定需求预算，并为 C1 六种投入品执行一次性价格边界迁移：开放玩家订单完整撤销并释放冻结资产，人口消费与市场储备订单释放后重建；存量库存、合同、拍卖和真实历史成交不得换算数量或重写。直接与派生订单仍必须逐笔冻结真实资金，成交、价差退款和撤单释放规则不变。

> 人口政策调控只改变后续人口稳定需求预算、钱包缺口补充和下一完整生产周期的人口工资系数，不得取消、改价或重建当前人口订单，也不得改变玩家订单、储备订单、生产成本或真实成交统计。当前市场需求模型为 18，人口经济内部版本为 7，资金精度版本为 3。


模型 16 保持 `food` / `household` 两个内部需求组和既有订单字段，全部 38 种商品均可形成 `direct` 买单；成交后商品被终端消耗，不进入人口库存。人口数量只改变聚合订单的资金规模和可购整数数量，不创建逐人口订单。模型升级必须先释放旧 `direct` / `derived-liquidity` 订单占用的人口冻结资金，再删除旧系统订单；市场储备的真实资金、库存和累计交易数据继续保留。

## 1. 统一资产模型

商品和工厂都使用 `AssetOrder`：

```ts
interface AssetOrder {
  id: string;
  provinceId: string;
  assetKind: 'commodity' | 'facility';
  assetId: string;
  productId?: string;
  facilityTypeId?: string;
  side: 'buy' | 'sell';
  ownerType: 'player' | 'population';
  ownerId?: number;
  ownerName: string;
  demandGroupId?: 'food' | 'household';
  demandTier?: 'direct' | 'derived-liquidity' | 'liquidity-buy' | 'liquidity-sell' | 'liquidity-emergency-sell';
  demandCycleId?: number;
  populationModelId?: 'basic' | 'skilled' | 'professional';
  fundingPool?: 'direct' | 'derived';
  fundingSlices?: Array<{ populationModelId: 'basic' | 'skilled' | 'professional'; fundingPool: 'direct' | 'derived'; reservedAmount: number }>;
  price: number;
  quantity: number;
  remaining: number;
  fills?: OrderFill[];
  status: 'open' | 'partial' | 'filled' | 'cancelled';
  createdAt: number;
  lastFilledAt?: number;
}
```

兼容字段 `provinceId` 与资产种类、资产 ID 共同组成订单簿身份。世界仍只保存一个 `world.orders` 数组，但运行时盘口、商品行情和工厂行情必须使用 `provinceId + assetKind + assetId` 分组；不同州级地区的同种商品或同类工厂不得互相撮合、互相形成五档深度、价格历史或估值。所有玩家订单、人口／储备系统订单和迁移订单都必须拥有地区；缺失值只在世界迁移时归入默认地区加利福尼亚州 `110000`。

`ownerType: 'population'` 是消费需求与市场储备商品订单在持久化、撮合、手续费和既有统计中的兼容标识，不表示继续使用旧人口需求模型。两类系统订单都沿用需求组兼容名称“食品市场需求”或“家庭消费市场需求”，必须通过 `demandTier` 区分消费与储备角色；预算、替代、互补、储备资产和价格传导以 `PRODUCT_AND_GAMEPLAY_DESIGN.md` 为唯一权威来源。

一级市场使用“商品目录 → 商品全局详情 → 地区商品详情”三级钻取；地图州上下文仍使用“地区商品目录 → 地区商品详情”短路径。商品全局详情只读取完整公开订单快照并按 `provinceId + assetKind + assetId` 分组展示各地区卖单量与买单量，绝不形成全国订单簿、全国深度或全国撮合。建筑资产订单簿只允许从建筑详情打开从属资产交易视图，返回时恢复原建筑详情；商品与工厂继续共享同一订单簿内核，但不得因此混入同一个可见目录。

商品列表和商品详情主视觉使用 `ProductArtwork`；建筑从属资产交易详情使用按正式 ID 映射的 `FacilityIcon`。订单表格、本地成交等紧凑商品标签继续使用对应 `ProductIcon`，紧凑工厂标签使用独立厂房 SVG `FactoryIcon`，不得使用机械商品的齿轮图标，也不得恢复 `⚙` 字符。图标只承担视觉语义，不改变资产 ID、撮合或估值规则。

地区商品目录和商品全局详情的地区行使用该地区官方系统价 `officialPrice` 与真实 24h 成交变化；基准偏离不在列表展示，只在具体地区商品详情计算。一级商品目录的跨州价格范围只能由各地区 `lastTradePrice` 形成，不得用 `officialPrice` 平均值、基础价或回退价制造全国市场价。`lastPrice` 与商品基础价只可用于详情行情曲线内部填补空分段和对照。建筑从属资产详情继续显示对应工厂订单簿的真实成交与行情。

市场下单表单与同资产五档订单簿必须位于同一个一级“{资产}交易”卡片内，内部使用无嵌套卡片的左右区域：下单区在左、订单簿在右，只以留白和分隔线区分。交易卡标题下固定显示最近成交、近 24h 变化和当前可用商品／可出售工厂的紧凑摘要；价格和数量均使用“字段标签／内嵌减号按钮／共享输入控件／内嵌加号按钮”的单行组合，价格步长为 0.01、数量步长为 1，快捷数量只显示 25%／50%／最大。最大可买／可卖、订单总额和可用资金／预计到账常驻显示，不再提供“交易资产详情”折叠区；资金、仓库、库存、冻结、抵押和生产参与只在摘要、限制说明或所属页面展示，市场不得重复堆叠。桌面端和移动端订单簿使用同一信息结构，均连续展示卖 5 至卖 1 和买 1 至买 5，不渲染“档位／价格／数量”表头或真实最近成交价“最新”分隔行；桌面端继续隐藏“实时五档 · 点击填价”辅助文案。档位可使用不遮挡文字的淡色深度比例背景，点击任一档位只把该档价格填入价格输入，不得直接提交订单。价格输入只在显式启用 `wheelStep={0.01}`、输入框已聚焦且滚轮命中输入框时按 0.01 调整并消费纵向滚轮；未聚焦时必须放行页面滚动。当前资产本人订单统一在详情后续“已有订单”区逐单展示和撤销，交易卡内不得再复制快捷撤单列表。内容宽度不小于 820px 时交易卡内部保持下单 60%／盘口 40% 双列；内容宽度不大于 819px 时继续使用约 60%／40% 左右双列，并给盘口保留不小于 112px 的可读宽度。不大于 `720px` 的移动端始终同时显示下单区和五档盘口，包括 `320px` 视口；极窄宽度通过把价格与数量标签移到输入框上方、压缩快捷数量间距、缩窄盘口三列并保留至少 44px 档位高度适配，不得隐藏任一区域、改为上下堆叠或恢复“下单／盘口”切换。“我的订单与成交”在桌面与移动端统一按“已有订单在上、本地成交在下”的单列顺序同时显示，不渲染“挂单／成交”账户视图切换，也不得通过断点隐藏其中一项。布局变化不得改变五档深度、撮合、冻结、手续费或订单限制。

`FacilityListing` 只允许作为历史迁移兼容空结构存在，不得重新成为业务模型。

消费需求与市场储备订单使用 `demandGroupId`、`demandTier` 和 `demandCycleId` 标记组别、角色与周期，但仍遵守同一价格优先、同价时间优先规则。就业收入预算按直接需求 70%／派生流动性 30% 分配，稳定预算按 85%／15% 分配；库存不得扩大消费预算，派生需求不得沿产业链重复发行。市场储备独立使用六位小数真实资金和整数真实库存挂出双边订单，每周期撤销重挂，不使用消费订单的跨周期保留。

### 1.1 人口资金字段隐私

`populationModelId`、`fundingPool` 与 `fundingSlices` 只用于服务器持久化、冻结和结算。集中式公开订单序列化必须删除这些字段，并继续删除所有订单来源、需求组和角色字段；普通玩家、本地成交记录和市场页面不得判断订单由哪类人口或多少人口账户共同资助。玩家在线自动交易可在服务器玩家私有状态分别保存“商品 → 本人自动买单订单 ID”和“商品 → 本人自动卖单订单 ID”关联，用于本人的在线重平衡；这些关联不得写入普通 `AssetOrder` 公共来源字段，也不得让其他玩家从公开订单 JSON 判断某张玩家订单是手动、自动采购还是自动出售创建。

## 2. 下单与冻结

所有订单均由服务器校验：

- 商品和工厂订单价格统一为不低于 0.01 的两位小数，最小价格步长为 0.01，不设置固定业务最高价；价格只受六位小数内部金额安全范围和单笔订单总额可表示范围约束。数量必须为正安全整数。账户余额、冻结、总额、手续费和退款保留六位小数。商品和工厂买卖单统一读取 `ECONOMY_CONSTANTS.maxOrderQuantity`，其值为 `Number.MAX_SAFE_INTEGER`，只表示技术安全边界，不构成固定业务数量上限。
- 买单和卖单都必须在冻结资产前校验单笔订单总额处于系统可表示金额范围内；超出范围时拒绝下单，不得截断、回绕或按 0 金额继续撮合。
- 每名玩家的商品和工厂订单合计最多同时存在 `(PRODUCT_CATALOG.length + FACILITY_TYPE_CATALOG.length) * 10` 笔未完成订单；上限必须始终由正式目录动态计算，不得在业务逻辑或防回退检查中固化旧目录数量。当前权威目录为 38 种商品与 26 种工厂类型，即当前上限 640 笔；目录增减时按商品与工厂类型总数的 10 倍自动变化。
- 每个玩家在每个地区的每种商品最多各有一张由服务器私有关联确认的在线自动采购买单和在线自动出售卖单；两类自动订单都不占用普通开放订单配额，普通手动订单不得伪造任一私有关联绕过上限。
- 玩家买单冻结对应资金。
- 消费需求订单不冻结玩家资金。三类人口先按角色和商品聚合六位小数预算，一张订单通过私有 `fundingSlices` 从一个或多个真实人口账户的可用余额转入冻结资金；直接与派生资金池通过 `fundingPool` 标记。成交按各切片精确扣款并退回限价与 maker price 的差额，撤单或缩量按原切片释放未成交冻结资金。
- 市场储备买单创建时从储备可用资金转入冻结资金，成交按 maker price 支出并退回价差，撤单释放未成交部分。
- 市场储备卖单创建时从储备可用库存转入冻结库存，成交扣除真实冻结库存并增加储备资金，撤单释放未成交部分。
- 当玩家卖盘为空、正常储备卖单无法形成且储备仍有真实可用库存时，允许创建内部 `liquidity-emergency-sell` 紧急储备卖单；其冻结、成交、撤单与普通储备卖单共用真实 `frozenInventory`，单档最多为目标库存 5% 且仍受基础价 50%～300% 与系统盘口非交叉约束。紧急储备成交的价格传导权重固定 25%，不得用于扩大预算或制造额外商品。
- 商品卖单只冻结订单地区的对应可用库存。
- 工厂卖单只冻结订单地区的对应工厂数量；可卖数量必须额外扣除银行抵押数量。
- 商品与工厂单项或捆绑拍卖也冻结卖方资产；拍卖冻结与订单簿冻结必须按资产 ID 合并计算，任何一方都只能使用扣除另一方冻结后的可用数量。工厂银行抵押不属于交易冻结且继续生产，但必须从订单簿卖单和拍卖的可转让数量中扣除。
- 撤单释放未成交部分资产。
- 部分成交只保留剩余数量对应的冻结资产。
- 同一玩家不得自成交。
- 玩家提交商品或工厂订单时，若新买价不低于本人同资产最低未完成卖价，或新卖价不高于本人同资产最高未完成买价，服务器必须在冻结任何资金、商品或工厂之前拒绝新订单，并提示先撤销原反向订单。
- 相等价格也属于交叉；不得只在撮合阶段跳过本人订单后，让两张交叉订单同时留在公开订单簿。
- 所有写操作使用 `Idempotency-Key`。
- 市场“自动交易”工作区继续复用商品订单写接口与正式撮合，不形成第二套订单类型。`execution: online-auto-buy` 与 `execution: online-auto-sell` 只表示一次由在线客户端发起的服务器权威订单维护请求；服务器必须重新读取玩家存档策略，不得相信客户端提交的阈值、价格或估算数量。自动采购买单以“生产预定 + 自动准备合同缺口 + 目标自由库存 - 当前可用库存”计算需求量，并按当前可用资金加当前关联自动买单可释放冻结资金计算可负担数量；自动出售以“当前可用库存 + 当前关联自动卖单剩余量 - 生产预定 - 自动准备合同缺口 - 最低自由库存”计算目标剩余量。达到价格的外部对手盘按统一撮合立即成交，未成交剩余分别作为真实开放买单或卖单留在统一订单簿。两类关联订单均不占普通开放订单配额；策略、价格或目标量变化时只撤销对应方向旧关联订单再重建，新单获得新的 `createdAt`。同方向价格和 `remaining` 目标未变化时必须保留原单时间优先级；目标为零时撤销而不重建。自动采购真实冻结玩家资金，自动出售真实冻结商品；离线期间不新增后台补挂、调价或重平衡扫描。双向同时启用时，采购目标自由库存必须不高于出售最低自由库存，且采购最高价必须严格低于出售最低价，防止策略自身形成反向交叉。
- 建厂一键购料属于现有商品订单簿的事务内 `Fill-or-Kill`（FOK）买入，不是系统商店：只采购建设所缺数量，按当前真实卖盘价格优先／同价时间优先逐档成交并继续使用 maker price、玩家卖出手续费、普通成交记录与市场储备真实库存。客户端必须提交逐材料价格上限与本次采购总额上限；服务器重新预扫盘口，价格下降按更低真实成交价执行，任一材料深度不足、价格超过上限、自成交、资金不足或最终建设失败时整个组合事务回滚。FOK 建材买单经过完整预检后必须在本事务全部成交并立即关闭，因此不占“同时未完成订单”数量上限，但其已完成订单与 fills 仍按普通真实交易保留。
- 当前卖盘不足时的建造采购组仍然不是第二套订单。`POST /api/game/orders` 的内部 `execution = facility-build-procurement` 是普通玩家订单“禁止自交叉”的唯一受控例外：服务器必须先校验本次建造原始缺口对应的逐材料买价，再自动撤销与这些买价交叉的本人同商品未完成 SELL；相等价格也属于交叉，高于买价的本人卖单不得撤销。撤单释放剩余冻结库存后必须重新计算真实建造缺口、未完成订单数量和新买单最大冻结额，释放库存已经补足的材料不得继续创建 BUY；若全部缺口因此归零则成功结束且不创建空采购组。随后仅对仍有缺口的材料批量创建普通玩家商品 BUY，每张子订单都进入唯一 `world.orders`，继续执行价格时间优先、maker price、资金冻结、部分成交、玩家未完成订单上限、成交记录和逐单撤销；由于交叉卖单已在同一事务中消除，子订单本身仍不得与任何剩余本人反向订单交叉。自动撤单、缺口重算与全部子订单创建属于同一个幂等经济回滚边界，后续订单额度、资金或任一子订单失败时必须恢复已撤销卖单及其冻结库存。普通手动订单和建厂 `Fill-or-Kill` 一键购齐仍保持原自交叉拒绝规则，不得扩展此例外。`execution = facility-build-procurement-cancel` 只批量调用同一玩家这些正式 BUY 的普通撤销语义；已成交数量不得回滚，剩余冻结资金正常释放。一次建造提交形成一个浏览器可见采购组，但组 ID 与订单关联仅用于当前玩家建设卡聚类，不写入公开 `AssetOrder`、不改变匿名序列化、不建立第二套盘口，也不改变市场页“我的订单”逐单展示和逐单撤销。采购完成不得自动创建工厂，建造现金不得作为订单冻结资金。

共享仓库永久无限；商品买单、商品拍卖和采购合同不预占仓库容量。商品买入的可执行数量只受资金、订单参数和技术安全边界约束，成交商品始终允许进入共享仓库。工厂买单和工厂竞拍同样不涉及仓库容量。

## 3. 工厂运行中卖出

运行中的未冻结、未抵押工厂允许进入卖单。

服务器提交工厂卖单时：

1. 结算已经完成的完整周期。
2. 从待加入数量和当前参与数量中冻结卖出数量。
3. 立即降低当前或下一周期参与数量。
4. 冻结数量停止产生商品和运营成本。
5. 保持剩余未冻结工厂的运行意图和周期语义。

撤销工厂卖单时，未成交数量解冻：

- 集群停止时立即恢复可用数量；
- 集群运行时进入 `pendingJoinCount`，从立即加入运行；
- 保持当前进度并同比稀释满员率，不生成部分周期产出。

## 3.1 拍卖与订单簿隔离

拍卖成交不属于订单簿成交。商品、工厂或捆绑拍卖的起拍价、当前最高价和成交总价不得进入 `AssetOrder`、订单簿买卖盘、`lastPrice`、`lastTradePrice`、价格历史、主动方向成交量、市场需求真实成交 VWAP 或资产估值；混合资产包总价不得拆分为虚构单价。订单簿冻结与拍卖冻结只在可用资产校验和工厂参与数量上合并，撮合、价格发现和成交统计保持独立。银行抵押数量继续参与生产，不进入两类交易冻结，但不能进入任何新工厂卖单或拍卖。

商品拍卖不预占买方仓库容量；同一资产包中的多种工厂与工厂卖单冻结数量共同退出生产。拍卖取消、无人出价、未达隐藏保留价或结算失败时释放对应冻结，成交时原子转移整个资产包，不创建伪造订单或成交明细。冻结资金、冻结商品和冻结工厂继续存在于各自权威余额中；拍卖发布费另行进入世界级托管余额，托管记录不得作为第二份资产余额重复计入玩家总资产。收费、保留价、延时和匿名竞价以 `GIFT_CODE_AND_ADMIN_DESIGN.md` 为唯一权威来源。

## 4. 撮合与非交叉不变量

撮合固定遵循：

1. 州级地区、资产种类和资产 ID 必须相同。
2. 价格优先。
3. 同价时间优先。
4. 最高买价大于或等于最低卖价时成交。
5. 允许部分成交。
6. 未成交部分继续保留。
7. 禁止自成交。
8. 成交、冻结、双方资产和统计在同一事务中更新。

商品订单和工厂订单不得互相撮合；不同地区、不同商品或不同工厂类型也不得互相撮合。不同主体之间可成交的同地区交叉订单必须在新订单进入订单簿时立即按 maker price 撮合，直到新订单完成、对手盘耗尽或最高买价严格低于最低卖价；不得先公开展示可成交交叉盘口再等待下一次轮询处理。`world.orders` 继续是唯一持久化权威订单集合；`order-book-runtime.js` 只为当前工作世界按地区、资产和方向建立价格时间优先索引，同价且时间相同时必须保持原数组顺序。索引识别尾部追加并对数组整体替换自动重建，订单成交、撤销和部分成交直接读取同一订单对象的当前状态；索引不得进入世界 JSON、客户端分区、分区哈希、估值或 SQLite。撮合、自交叉、系统最优价、玩家未完成订单数量、商品买单预占、工厂卖单冻结和人口卖盘深度不得各自重新对完整 `world.orders` 过滤排序。

运行时索引必须保持一个按资产与方向组织的统一混合盘口，玩家订单、消费需求订单和市场储备订单不得拆成独立玩家盘口或系统盘口。全量建立索引时必须先单次遍历未完成订单完成分组，再对每个既有分组统一排序；不得在全量构建循环中逐单对有序数组执行中部 `splice`。已成交或已撤销订单只保留在 `world.orders` 历史中，不进入活动盘口、玩家开放订单集合或需求组开放订单集合。尾部新订单仍可二分插入当前分组；成交缩量与撤单必须同步更新运行时开放订单计数、商品买单预占和工厂卖单冻结聚合。当前版本迁移、无变化历史剪枝和不存在旧系统工厂订单的清理必须保持原 `world.orders` 数组引用；真实剪枝只淘汰过期或超过 800 笔的已关闭历史，不得因历史保存上限删除任何未完成订单。需求周期结算仍可在同一运行时中维护按需求组组织的轻量订单历史集合，以读取本周期已经成交或撤销的需求订单；该历史集合不得作为第二套盘口，不参与价格排序、撮合候选、玩家开放订单计数、仓库预占或工厂冻结聚合。

消费需求买单只能与同商品的玩家卖单成交；市场储备买单和卖单只能与玩家订单成交，任何两个 `ownerType = population` 的系统订单都必须排除。消费需求成交必须记录 `lastFilledAt` 并在下一完整周期统一结算，直接需求独立累计请求、成交和延迟得分。每项商品保存双向报价锚点（六位小数）、连续过剩周期与虚拟预算赤字；锚点按模型 13 延续的零成交、成交不足、持续过剩和短缺规则平滑，合法范围为 0.01 至基础价 300%，最终买价向下量化到两位小数。三类人口预算先按资金池和商品聚合，计算最大可负担整数数量后再按 50%／30%／20% 拆档。旧订单最多存在三个周期，成交率低于 25% 保留剩余 70%，25%～80% 保留 35%，高于 80% 撤销；单商品与需求组价值保护继续保持 1.5 倍和 2.5 倍。

系统订单不能用系统自成交清除交叉，因此报价生成器必须主动维护以下不变量：

```text
同一商品同时存在系统买盘和系统卖盘时：
最高系统买价 < 最低系统卖价
```

具体规则：

- 储备卖价必须至少为当前最高系统买价加 0.01。
- 储备买价必须至多为当前最低系统卖价减 0.01。
- 报价仍必须位于商品基础价 50%～300% 的合法区间，并保留储备自身买价低于卖价的动态价差。
- 无法在合法区间内避让时，不创建对应方向的储备订单；不得压低消费需求订单、制造系统成交或突破价格边界。
- 每轮系统订单生成后必须重新检查系统盘口；若异常状态仍交叉，优先取消当前周期的储备卖单，其次取消当前周期的储备买单，并原额释放冻结库存或冻结资金。
- 交叉修复只允许重新定价、跳过报价或撤销储备订单，不得生成 fill、成交量、价格历史、估值变化、手续费或排行榜交易额。

公开订单簿的长期稳定状态不得包含可成交的不同主体交叉订单、同一玩家交叉订单或系统交叉订单。瞬时函数调用内部可以在新订单创建后立即进入撮合，但事务返回和客户端状态序列化之前必须恢复非交叉状态。

### 4.1 共享撮合内核

`server/src/order-matching.js` 是商品与工厂限价订单的唯一撮合状态机。商品 `balanced-market.js` 与工厂 `facility-groups.js` 必须调用同一个 `matchIncomingOrder`，不得各自重新实现候选排序、价格交叉判断或逐笔成交循环。

共享内核统一负责：

- 同资产、反方向和有效未完成订单筛选；
- 价格优先、同价时间优先；
- 同一玩家自成交的最后一道阻断；
- resting order 作为 maker，并使用 maker price；
- 部分成交数量、`remaining`、`status` 与 `lastFilledAt` 推进；
- `makerOrderId`、`takerOrderId`、`liquidity`、手续费与净额字段的逐笔 fill；
- 统一调用玩家卖方手续费规则。

资产适配器只允许负责自身业务结算与行情记录：商品适配器转移玩家库存、真实人口冻结资金和市场储备资产；工厂适配器转移工厂集群数量并维护生产参与状态。共享内核不得导入商品目录、工厂目录、仓库或生产规则，适配器也不得重新实现排序、maker/taker、fill 或订单状态推进。历史迁移和运行时新订单必须复用同一内核，避免两类资产形成不同撮合语义。

## 5. maker price 与逐笔成交

每次成交使用撮合前已经位于订单簿中的对手方挂单价格，即 maker price。

服务器在相关订单 `fills` 中逐笔保存：

```ts
interface OrderFill {
  id: string;
  quantity: number;
  price: number;
  total: number;
  fee: number;
  netTotal: number;
  counterparty: string;
  createdAt: number;
  makerOrderId: string;
  takerOrderId: string;
  liquidity: 'maker' | 'taker';
}
```

同一订单扫过多个价格时必须生成多条独立成交明细，不得合并为平均价。浏览器不得使用市场 `lastPrice` 反推玩家成交价，也不得以最终市场价覆盖真实逐笔价格。

订单簿和价格曲线属于市场状态；玩家成交记录属于订单级权威明细。两者不得互相替代。

### 5.1 玩家卖出手续费

统一订单簿只向玩家卖方收取手续费，买方仍按 `quantity × maker price` 支付完整成交总额。商品卖单、工厂卖单以及玩家卖给“食品市场需求”“家庭消费市场需求”“食品市场储备”或“家庭消费市场储备”买单的成交使用同一规则；玩家从储备卖单买入时玩家不是卖方，不收取玩家卖出手续费。拍卖结算不属于订单簿，不调用本节累计卖单手续费函数，也不生成 fill；拍卖使用自身规则快照向卖方收取最终成交总价精确 1% 的独立手续费，并另有发布费，资金同样进入市场服务就业收入。两者费率相同不代表业务模型或累计字段可以复用。

手续费按单张卖单自规则启用后的累计成交总额精确计算，不设置最低手续费：

```text
累计应收手续费 = roundToMicros(累计成交总额 × 1%)
本次 fill 手续费 = 累计应收手续费 - 此前累计已收手续费
本次卖方实收 = 本次成交总额 - 本次 fill 手续费
```

手续费从第一笔成交开始按六位小数累计，不设置最低金额；例如累计成交额 9.99 时累计手续费为 0.099900。拆单或部分成交不能改变同一卖单的累计费率。

`fill.total` 始终保持成交总额，卖方 fill 的 `fee` 表示本笔增量手续费，`netTotal` 表示本笔实际到账。手续费不再进入 `systemSinks`，而是按基础人口 20%、技术人口 60%、专业人口 20% 转入市场服务待结算收入。人口消费成交从真实人口冻结资金支付，禁止增加 `populationIssued`。

上线迁移不得追收既有成交：旧卖单第一次发生新成交时，已有 fill 保留原值，V2 累计字段从 0 开始，只对启用后的新 fill 收费。服务器必须在同一成交事务完成扣费、就业转移和 fill 标记，幂等重试或状态轮询不得重复扣费。

### 5.2 行情主动方向

商品和工厂每笔成交除价格、数量和时间外，还必须保存吃单方（taker／incoming order）的买卖方向。主动买单吃掉已有卖单时记为主动买入，主动卖单吃掉已有买单时记为主动卖出；不得把成交双方的买卖数量直接相减，也不得按价格涨跌猜测主动方向。

概览页与市场页共用同一最近 24h、6 分钟行情分段。分段收盘价取最后一笔成交价，总成交量为全部成交数量之和，净主动量为主动买入量减主动卖出量。成交量柱高表示总成交量，颜色只表达净主动方向：净买入使用成功色，净卖出使用危险色，均衡或旧历史方向未知使用中性色。旧成交没有主动方向字段时必须保留为中性成交量，新成交逐步替换该窗口，禁止伪造迁移方向。

## 6. 单列价格档位订单簿

每个选中资产的桌面订单簿固定显示：

```text
卖 5 至卖 1（最低卖价靠近买盘）
买 1 至买 5（最高买价靠近卖盘）
```

桌面端和不大于 `720px` 的移动端使用同一连续五档结构，均不显示重复的“档位／价格／数量”表头，也不在卖盘与买盘之间增加“最新”分隔行；最近真实成交价由详情摘要显示。

每行只显示：

```text
档位｜价格｜合计剩余数量
```

规则：

- 同资产、同方向、同价格的有效订单按当前剩余数量聚合为价格档位。
- 有效订单只包括 `open` 或 `partial`、`remaining > 0` 且价格为不低于 0.01 的两位小数订单；已成交、已取消和零剩余订单不得进入档位。
- 聚合只累加 `remaining`，不得累加原始 `quantity`，并记录档位内独立订单笔数用于无障碍名称。
- 必须先聚合全部有效订单，再按买盘价格降序或卖盘价格升序排序，聚合完成后再按最优价格截取 5 档；不得先截取 5 笔订单再聚合。
- 卖盘视觉上将已选出的最优 5 档反向排列并标为卖 5 至卖 1，使最低卖价直接靠近买 1；买盘按最高价到最低价标为买 1 至买 5。
- 最近成交摘要只读取同资产 `lastTradePrice`；无真实成交时显示“—”，不得用 `lastPrice`、基础价、系统价值或挂单价伪装，任何断点都不得恢复盘口“最新”分隔行。
- 每档允许按当前聚合剩余量显示不遮挡文字的淡色水平深度比例背景；颜色只表达买卖方向，不作为唯一信息。
- 点击任一档位只把该档价格填入价格输入，不改变订单方向、数量或其他草稿，也不得直接提交订单、冻结资产或触发撮合。
- 档位聚合只属于客户端匿名展示，不改变服务器 `AssetOrder`、价格优先、同价时间优先、部分成交、冻结、逐笔 fill、撤单和单张卖单手续费。
- 不显示玩家身份或市场需求身份；玩家订单与市场需求订单同价时使用相同档位结构。
- “我的当前资产未完成订单”和“我的订单与成交”继续逐单显示，使用独立订单 ID 单独撤销，不得按档位合并。
- 桌面订单簿按内容自然高度显示；订单不足时不生成虚假空行，也不得与行情卡强制等高。
- 移动端按内容自然增长；常见手机与下单区同排时可以压缩字距和列宽，但不得隐藏档位、价格或数量列。

## 7. 下单界面与默认价格

玩家界面统一将订单输入字段称为“价格”，不得显示“限价”字段、标题或表头。底层订单仍是限价订单模型，服务器撮合、冻结和校验规则不变。

界面顺序固定为：

```text
资产列表整行入口
详情资产摘要
最近成交／24h 变化／可用资产摘要
买入｜卖出
价格：减号按钮｜共享 MoneyInput｜加号按钮
数量：减号按钮｜共享 IntegerInput｜加号按钮
25%｜50%｜最大
最大可买／可卖｜订单总额｜可用资金／预计到账
提交买入／卖出
近 24h 价格与成交量曲线
当前资产已有订单与撤单
当前资产本地成交
```

价格和数量均使用“减号按钮／共享输入控件／加号按钮”。价格按钮每次调整 0.01，数量按钮每次调整 1；按钮必须复用与输入字段相同的最小值、最大值、资金、仓库、库存、工厂可出售量和技术安全整数校验，达到边界后禁用，不得通过步进绕过解析、截断、错误提示或订单上限。25%／50%／最大快捷数量继续按当前方向和资产类型计算；“最大”只是填入当前合法最大数量，不直接提交。

默认价格只从客户端当前已经加载的 `game.orders` 本地快照计算，不得为填写默认价格调用 `getGameState`、`refresh`、新增 API 或发起任何额外网络请求。

只考虑同资产种类、同资产 ID、`open` 或 `partial`、剩余数量大于零且价格为不低于 0.01 的两位小数订单：

```text
买入：最低卖出价
      → 没有卖单时使用最高买入价
      → 买卖盘均为空时使用 1

卖出：最高买入价
      → 没有买单时使用最低卖出价
      → 买卖盘均为空时使用 1
```

重新填写默认价格的时机：

- 从商品列表打开商品详情，或从建筑详情打开建筑资产交易；
- 从其他页面重新进入当前资产所属详情；
- 主动切换商品，或从另一建筑打开不同建筑资产；
- 主动切换买入／卖出方向。

自动刷新、下单响应、成交、撤单或其他权威状态同步只更新本地订单快照，不得直接覆盖当前价格输入。玩家下一次重新进入市场、切换资产或切换方向时，使用届时最新的本地订单快照重新计算。

在市场页内再次点击当前已经选中的资产或当前方向时，不重新填写价格，保留玩家手动输入。默认价格不得使用 `lastPrice`、商品 `basePrice`、工厂 `systemValue` 或正式估值价格作为回退。

商品买入快捷数量只受当前可用资金、价格与技术安全整数边界约束，不读取或模拟仓库剩余容量。

商品卖出快捷数量使用当前可用库存。冻结商品不能出售。

工厂买卖快捷数量使用当前可用资金或未冻结工厂数量，不使用共享仓库容量。

## 8. 订单来源与模型迁移

商品订单只允许玩家、消费需求或市场储备作为所有者：

- 玩家可以提交商品买单和卖单。
- 消费需求只提交买单，名称只能是“食品市场需求”或“家庭消费市场需求”，`demandTier` 只能是 `direct` 或 `derived-liquidity`。
- 市场储备可以提交商品买单和卖单，继续沿用所属需求组的兼容名称，`demandTier` 分别为 `liquidity-buy` 或 `liquidity-sell`；不得根据 `ownerName` 判断订单角色。
- 持久化字段 `ownerType = 'population'` 只是两类系统商品订单的兼容标识。
- 储备买单必须由真实储备可用资金全额冻结；储备卖单必须由真实储备可用库存全额冻结。不得创建无资产支持的系统订单，不得在普通周期补发储备资产。
- 消费需求和市场储备订单不得互相成交，任何系统订单之间都不得成交。
- 消费需求按就业收入 70%／30%、稳定预算 85%／15% 分配直接与派生资金；三类人口按商品聚合预算并使用私有 `fundingSlices`，旧买单按成交率保留且最多存在三个周期。市场储备每周期释放旧冻结并按真实资产、0.01 价格步长、安全库存和无业务总量上限规则重新报价。
- 不生成企业采购或普通人口需求，也不创建任何系统工厂买单、系统工厂卖单或固定价格工厂供给。

模型迁移规则：

- 模型 3 升级到 4 时一次性初始化储备资金和商品种子，并立即生成消费买单与储备买卖单。
- 模型 4 升级到 5 时必须删除全部旧系统商品订单，先把每个储备组的冻结资金原额退回可用资金、把每种商品的冻结库存原额退回可用库存，再按非交叉规则重建系统盘口。
- 模型 5 迁移不得改变玩家资金、商品、工厂、玩家订单、玩家订单冻结资产、成交记录或价格历史，也不得重复发行储备资金和商品种子。

工厂订单仍只能由玩家提交；服务器周期、迁移、刷新和进入游戏都不得创建工厂订单。

## 9. 估值与排行榜

商品估值价格使用官方系统价 `officialPrice`；工厂估值价格使用：

```text
商品：该州该商品当前官方系统价（officialPrice）
工厂：该工厂最近一次订单簿真实成交价（lastTradePrice）
```

- 只有统一订单簿撮合生成、带真实买卖主动方向的成交才能更新 `lastTradePrice`；玩家与市场储备的成交属于真实成交，但在需求价格传导中只使用 50% 信号权重。官方系统价在每个价格周期结算后写入行情曲线。
- 新世界的模拟价格历史、商品 `basePrice`、工厂 `systemValue`、当前 `lastPrice`、买卖挂单价格和拍卖价格都不得充当工厂最近真实成交价。
- 工厂从未发生订单簿真实成交时估值为 0；界面必须显示货币 0，不得显示 `--`。
- 商品估值数量包含可用和冻结库存。
- 工厂估值数量包含玩家拥有的全部数量，包括卖单、拍卖冻结和银行抵押数量。
- 银行存款计入现金资产，未偿贷款本金与未付利息作为负债从资产毛值中扣除；统一订单簿只负责商品和工厂估值价格，不负责贷款额度或利息。
- 净资产、资产摘要和财富排行榜由服务器统一计算。
- 客户端不得使用任意挂单价、基础价、系统价值或拍卖价替代商品官方系统价或工厂正式估值。

## 10. 本地成交

浏览器本地成交记录只比较相邻权威状态中新出现的 fill ID，并使用匿名 `fill.price`、`fill.quantity`、`fill.total`、`fill.fee`、`fill.netTotal` 和 `fill.createdAt`；不得读取或推断对手信息。

## 普通玩家订单与成交匿名化

服务器内部订单继续保存真实所有者、需求组和 maker/taker 关系，用于撮合、结算、市场需求货币发行统计和管理员审计。普通玩家状态必须经过集中式公开订单序列化：本人订单仅增加 `isOwn: true` 并返回由 `id / quantity / price / total / fee / netTotal / createdAt` 组成的匿名 fills；其他订单返回 `isOwn: false` 且不返回 fills。

普通玩家状态中的所有订单都不得返回真实 `ownerId`、`ownerName`、`ownerType`、`demandGroupId`、`demandTier` 或 `demandCycleId`。公开 fill 不得返回 `counterparty`、`makerOrderId`、`takerOrderId` 或 `liquidity`。消费需求、市场储备与玩家订单在普通玩家 JSON 中必须使用相同结构，不能通过字段差异判断来源。自动采购与自动出售的私有订单 ID 关联只属于当前玩家自己的市场自动交易策略状态，不得附着到其他玩家可见的订单字段上。

客户端通过 `isOwn` 识别本人订单，并只显示订单部分成交、全部成交、成交数量、价格、总额、手续费、实收和时间。隐藏界面列不能替代 API 脱敏。

## 市场页面布局与可用性

市场页固定使用同一页面内的商品列表与商品详情，不新增一级市场路由。列表只显示商品，并提供名称、正式目录分类和市场状态筛选；市场状态至少覆盖真实成交、买盘、卖盘、消费需求未满足和本人订单；排序通过点击列表表头完成，不占用筛选面板。筛选只投影当前客户端已经加载的当前地区状态，不产生写入或额外网络请求。点击整行进入详情，详情返回时保留筛选与表头排序；从建筑详情打开的工厂资产交易属于建筑页从属视图，返回原建筑详情。

市场交易主区按实际内容宽度响应：

- 列表筛选栏只保留分类与市场状态两项，按市场内容宽度降为单列；目录不得提供商品／工厂类型切换；
- 桌面与移动端商品行统一为“商品身份｜卖单量｜买单量｜市场价｜24h｜箭头”的紧凑单行结构，具体列规则以 `PAGE_CONTENT_AND_NAVIGATION_DESIGN.md` 与 `UI_DESIGN_SYSTEM.md` 为唯一权威，不得恢复挂单差额、基准偏离或挂单状态列；
- 详情交易卡内部在支持宽度下保持下单与盘口同排；行情图和当前资产订单／成交随后显示；
- 不大于 `720px` 时账户记录使用“挂单／成交”切换并只显示当前分区；下单与盘口仍同时可见，不恢复表头或最新成交分隔；
- 大于 `720px` 时隐藏账户“挂单／成交”切换和“实时五档 · 点击填价”辅助文案；
- 响应式必须使用市场内容容器宽度，不能只依赖浏览器视口或侧栏外的全局断点；仅桌面／移动可见性的边界统一使用 `720px` 浏览器视口。

完整行情图继续使用组件计算的动态几何，成交量绘图区必须保留最低可读高度和占比，不得由业务 CSS 恢复固定 `16:9`。市场复用概览与建筑相同的紧凑战略容器，行情图固定位于交易卡之后；不得因浏览器视口变宽而绕过页面容器恢复并排，也不得恢复已删除的行情底部统计栏。零涨跌使用中性色并显示 `0`，不得显示绿色 `+0`。

下单界面在当前条件无法提交时必须显示明确的文字原因，并同步禁用数量输入、快捷数量与提交按钮。不得通过 `Math.max(1, maxTradeQuantity)` 伪造可交易上限；资金不足、仓库不足、商品无库存和工厂无可售数量必须分别说明。价格与数量的减号／加号按钮必须满足移动触控尺寸，并保持共享输入控件的键盘焦点与错误语义。

桌面连续五档订单簿的视觉与 DOM 顺序固定为：

```text
卖 5 至卖 1（最低卖价靠近买盘）
买 1 至买 5（最高买价靠近卖盘）
```

## 市场需求模型 16 订单簿约束

- 市场需求模型版本为 14。实际人口只改变每周期聚合预算和订单数量，不增加人口订单主体或逐人口订单。消费需求订单在每个周期开始时先结算上一周期整个时间窗内的成交，再发布新订单。
- 同一商品的新消费预算按 50%／30%／20% 形成三档买盘；旧消费订单最多存在三个周期，并按累计成交率保留 70%／35%／0%；不得固定每周期提高 3%。
- 单商品消费买盘价值上限为本周期该商品分配预算的 1.5 倍，需求组总买盘价值上限为周期预算的 2.5 倍。
- 成交价格历史内部记录 `marketRole = player | consumption | liquidity`；预算活跃度只统计 `player`，价格观察允许 `consumption` 100% 和 `liquidity` 50% 权重。普通玩家 API 不得暴露该内部角色。
- 商品供需压力允许低于 1 表示公开供给过剩，不得恢复只取历史最大压力的单向实现。
- 市场储备仍使用真实可用资金和库存，任何系统订单之间都不得成交，且最高系统买价必须严格低于最低系统卖价。

## 价格与结算精度边界

订单价格以六位微单位核心保存和比较，但必须是 `10,000` 微单位的整数倍，即价格步长固定为 `0.01`。玩家输入超过两位小数必须拒绝；系统买价向下量化到价格步长，系统卖价向上量化到价格步长。成交总额使用“价格微单位 × 整数数量”，卖方累计手续费和净收入使用六位微单位，不得先转为两位账户金额。

## 官方系统价市场

世界 31 起，每个州×商品在本地市场状态中维护唯一官方系统价 `officialPrice`，作为玩家即时交易的固定执行价和商品估值口径。官方系统价在一个价格周期（默认与市场需求周期同为 5 分钟）内保持不变，周期结束按该周期系统成交的买卖量调整。

### 实时清算

- 玩家手动买单、自动采购买单、自动出售卖单和建厂采购订单照常先进入统一订单簿并按现有价格时间优先、maker price、冻结与手续费规则撮合。
- 玩家商品买单价格恰好等于官方系统价时，玩家撮合完成后剩余数量由系统按官方系统价实时全部供给：系统生成商品、回收玩家冻结资金，`cycleBuyQuantity` 增加。
- 玩家商品卖单价格恰好等于官方系统价时，玩家撮合完成后剩余数量由系统按官方系统价实时全部买入：系统销毁商品、按现有 1% 卖出手续费向玩家结算并计入市场服务就业，`cycleSellQuantity` 增加。
- 价格不等于官方系统价的玩家订单继续挂盘等待玩家间撮合或下一次调价瞬间被系统清算。
- 人口消费订单和市场储备订单不是官方系统价的对手方；系统只与玩家订单清算。
- 玩家间每笔成交同时包含买卖双方，不得计入系统买卖比；只有玩家与系统实际成交的数量计入 `cycleBuyQuantity`／`cycleSellQuantity`。

### 周期调价

每个周期冻结 `cycleBuyQuantity`（B）与 `cycleSellQuantity`（S）后按以下公式计算下一周期价格：

```text
imbalance = (B - S) / (B + S + 2L)
changeBps = clamp(round(imbalance × K), -MAX_CHANGE_BPS, +MAX_CHANGE_BPS)
nextPrice = clamp(officialPrice × (1 + changeBps / 10000))
```

默认参数：`L = 8` 为每种商品的虚拟流动性基线，`K = 100`（即 1%），`MAX_CHANGE_BPS = 50`（单周期最多 ±0.5%）。价格保留 0.01 步长并限制在基础价 50%～300% 边界内；无系统成交时 `imbalance = 0`，价格不变。调价结果写入行情曲线（无主动方向），随后立即扫描订单簿：所有恰好等于新官方系统价的玩家卖单由系统全部买入、玩家买单由系统全部供给，这些成交计入下一周期计数器，不得递归影响本次调价。

### 经济守恒与审计

系统向玩家出售商品即生成商品并回收货币；系统向玩家买入商品即销毁商品并发行货币。`world.systemMarketAudit` 按州×商品累计系统卖出／买入数量、货币回收／发行金额和成交笔数，只用于服务器审计，不进入普通玩家状态、行情、估值或六分区。

跨州运输只移动本地仓库商品，不创建订单、不参与撮合、不写入本订单簿；运输中的商品按起始州官方系统价计入玩家财富，到达目的州后进入该州本地仓库并按其官方系统价估值。跨州订单仍被禁止，运输是跨州商品流动的唯一渠道。

## 合同资产锁定

玩家贷款抵押和工厂出租属于合同锁定，不进入订单簿挂单量。所有银行抵押与合同锁定必须按 `provinceId + facilityTypeId` 归属；工厂可转让数量只扣除同一地区同类工厂的卖单、拍卖、银行抵押、玩家贷款抵押和出租数量，租入数量永远不可转让。合同利率、租金、供货价格和违约处置不得写入统一订单簿最近成交价、行情曲线或估值。

### 模型 19 系统需求重建

市场需求模型版本：19。模型 19 的系统需求重建只取消并释放人口消费和市场储备拥有的开放订单及其真实冻结资金／库存；玩家开放订单继续保留。新增工业燃料和工业化学品与其余正式商品共用同一商品订单簿、冻结、maker price、手续费、自成交阻断和匿名成交规则。

### 客户端订单索引性能边界

客户端允许针对当前收到的 `orders` 数组建立只读派生加速器形式的客户端订单索引，用于市场展示、自己的未完成订单统计和在线自动交易状态判断。该索引可以维护订单 ID 查询、按资产分组的开放订单、自己的开放订单，以及商品自己的／外部的最高买价和最低卖价；只有 `market.orders` 实际变化时才重建。

客户端订单索引只是查询加速器，不是第二套订单簿，不得撮合、冻结、成交、收费、改变 FIFO、决定 maker price 或绕过服务器校验。服务器 `order-book-runtime.js` 与统一撮合内核仍是订单状态和价格时间优先的唯一权威来源。索引中的对象必须直接引用当前权威订单快照，不得复制或持久化可产生另一份订单状态的数据。
